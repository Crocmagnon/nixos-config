# Odoo sur srv-1 — plan d'implémentation

> **Pour les agents :** SOUS-SKILL REQUISE — utiliser `superpowers:subagent-driven-development` (recommandé) ou `superpowers:executing-plans` pour exécuter ce plan tâche par tâche. Les étapes sont en cases à cocher (`- [ ]`).

**But :** faire tourner Odoo 19 sur srv-1, accessible en Tailscale seulement, avec sa base PostgreSQL sur l'instance OVH Web Cloud Databases `ag56382-001`.

**Architecture :** le module nixpkgs `services.odoo` fournit le paquet, l'unité systemd et le fichier de configuration ; on désarme le PostgreSQL local qu'il allume en dur et on pointe les options `db_*` vers OVH. Le mot de passe ne transite pas par le store : il arrive en `PGPASSWORD` depuis un `EnvironmentFile` agenix et c'est libpq qui le ramasse. Caddy expose le tout derrière `import internal`.

**Pile :** NixOS 25.11, `pkgs.odoo19`, PostgreSQL 17 (OVH, distant), agenix, Caddy, Terraform (provider `ovh/ovh`).

**Spec :** `docs/superpowers/specs/2026-09-22-odoo-srv-1-design.md`

## Contraintes globales

Valeurs à reprendre telles quelles, elles conditionnent plusieurs tâches :

- Hôte et port de la base : `ag56382-001.eu.clouddb.ovh.net:35458`
- Nom de la base et de l'utilisateur : `odoo` / `odoo`
- Paquet : `pkgs.odoo19`, posé explicitement — le défaut du module suit le `stateVersion`, et une bascule silencieuse de version majeure se paie en migrations non jouées
- `odoo19` tire `python3.12-pypdf2-3.0.1` (six CVE, fork abandonné). Exception **assumée** : `nixpkgs.config.permittedInsecurePackages = [ "python3.12-pypdf2-3.0.1" ]`, épinglée à la version exacte. Les alternatives et la raison du choix sont dans la spec
- PostgreSQL 17, 200 connexions simultanées annoncées sur l'instance
- Budget de connexions Odoo : `workers = 3`, `db_maxconn = 4`, soit 6 processus × 4 = 24 au pire
- Nom d'hôte HTTP : `odoo.srv-1.augendre.info` (temporaire, sur le modèle de `pdf.srv-1.augendre.info`)
- Accès Tailscale uniquement : `import internal` dans le vhost, **et** `http_interface = "127.0.0.1"` dans les options Odoo — le défaut d'Odoo 19 est `0.0.0.0`, ce qui court-circuiterait Caddy
- Le secret ne contient que `PGPASSWORD=…`, jamais `db_password` dans `services.odoo.settings`
- Pas de sauvegarde dédiée de la base dans ce plan : on s'en remet aux sauvegardes automatiques OVH

## Ce qui n'est pas automatisable

Ce plan touche deux dépôts et une console web. Un agent peut faire **la tâche 4 seule**. Les tâches 1, 2, 3, 5 et 6 demandent quelqu'un au clavier : espace client OVH, `terraform apply`, `agenix -e` (clé privée), déploiement sur srv-1, interface Odoo. Le plan les décrit intégralement quand même, pour qu'elles se déroulent sans réflexion.

### Tâche 2 : lever les deux inconnues bloquantes

Rien n'est écrit côté Nix tant que ces deux points ne sont pas tranchés. Chacun a un repli connu, mais chacun change le code de la tâche 4.

**Fichiers :** aucun. C'est un spike, on ne garde rien de ce qui est produit ici.

**Interfaces :**
- Consomme : la base et le mot de passe de la tâche 1.
- Produit : deux réponses oui/non qui décident du contenu de `hosts/srv-1/services/odoo.nix` (tâche 4), et une base `odoo` initialisée si tout va bien.

- [ ] **Étape 1 : lancer Odoo à la main depuis srv-1**

Cette unique commande répond aux deux questions : est-ce que `PGPASSWORD` atteint psycopg2, et est-ce qu'Odoo 19 démarre sur PostgreSQL 17.

```bash
ssh srv-1
env NIXPKGS_ALLOW_INSECURE=1 PGPASSWORD='<le mot de passe de la tâche 1>' \
  nix run --impure nixpkgs#odoo19 -- \
  --db_host=ag56382-001.eu.clouddb.ovh.net \
  --db_port=35458 \
  --db_user=odoo \
  -d odoo -i base --without-demo --stop-after-init
```

- [ ] **Étape 2 : lire le résultat**

**Résultat obtenu le 2026-09-22 :** `Modules loaded.`, `Registry loaded in 229.331s`, arrêt propre. 14 modules installés, confirmés par `SELECT count(*) FROM ir_module_module WHERE state = 'installed'`. Les deux inconnues sont levées et **la base est initialisée** : l'étape 3 de la tâche 5 est à sauter.

La commande a tourné **depuis srv-1**, avec `PGPASSWORD` exportée au préalable plutôt que posée sur la ligne de commande, pour ne pas la laisser dans l'historique fish. L'inconnue n°1 est donc levée dans les conditions réelles : Odoo ne passe aucun mot de passe à psycopg2 et libpq le résout depuis l'environnement. Il ne reste qu'à confirmer que systemd livre bien la variable via l'`EnvironmentFile`, ce que vérifie la tâche 5.

**Premier repère de latence, depuis srv-1 :** le module `base` a chargé en 101 s pour 8377 requêtes, soit ~12 ms par requête. C'est de l'initialisation, dominée par du DDL et du chargement de données XML, donc non représentatif d'un affichage de page. Mais c'est le seul chiffre dont on dispose avant la tâche 6, et il n'est pas rassurant : à 12 ms l'aller-retour, une page Odoo à 300 requêtes coûterait 3,6 s de latence pure. L'étape 6 de la tâche 6 doit mesurer un `SELECT 1;` pour séparer la latence réseau du travail réel.

| Ce qu'on voit | Ce que ça veut dire | Suite |
|---|---|---|
| `Modules loaded.` puis sortie en code 0 | les deux inconnues sont levées, **et la base est initialisée** | tâche 3, et sauter l'étape d'init de la tâche 5 |
| `FATAL: password authentication failed` ou `no password supplied` | `PGPASSWORD` n'atteint pas psycopg2 | appliquer le repli A (ci-dessous) en tâche 4 |
| une erreur de version PostgreSQL au démarrage | Odoo 19 refuse PG 17 | rétrograder sur `pkgs.odoo18` en tâche 4 — il n'a alors plus besoin de l'exception `permittedInsecurePackages` |

**Repli A — le mot de passe par un fichier de configuration à l'exécution.** Si `PGPASSWORD` ne passe pas, la tâche 4 ajoute au module :

```nix
{ config, lib, pkgs, ... }:
let
  # Même INI que celui que génère le module, régénéré ici pour ne pas avoir à le
  # lire depuis serviceConfig.Environment (qu'on est justement en train d'écraser).
  odooCfg = (pkgs.formats.ini { }).generate "odoo.cfg" config.services.odoo.settings;
in
{
  systemd.services.odoo.serviceConfig = {
    RuntimeDirectory = "odoo";
    Environment = lib.mkForce [ "ODOO_RC=/run/odoo/odoo.conf" ];
    ExecStartPre = lib.mkBefore [
      (pkgs.writeShellScript "odoo-conf" ''
        install -m0400 ${odooCfg} /run/odoo/odoo.conf
        printf 'db_password = %s\n' "$PGPASSWORD" >> /run/odoo/odoo.conf
      '')
    ];
  };
}
```

`EnvironmentFile` s'applique aussi aux `ExecStartPre`, donc `$PGPASSWORD` y est disponible. Le fichier atterrit dans `/run`, en `0400`, jamais dans le store.

### Tâche 4 : le module NixOS

C'est la seule tâche exécutable par un agent de bout en bout : tout se vérifie par `nix eval` et `nixos-rebuild dry-build`, sans toucher à srv-1.

**Fichiers :**
- Créer : `hosts/srv-1/services/odoo.nix`
- Modifier : `hosts/srv-1/services/default.nix` (ajouter `./odoo.nix` à la liste `imports`)

**Interfaces :**
- Consomme : `config.age.secrets."odoo-env".path` (tâche 3) ; le snippet Caddy `(internal)` et `(common_headers)` définis dans `hosts/srv-1/services/caddy.nix`.
- Produit : l'unité `odoo.service` écoutant sur `127.0.0.1:8069` (HTTP) et `127.0.0.1:8072` (websocket), le vhost `odoo.srv-1.augendre.info`, et le fichier INI pointé par `ODOO_RC`.

- [ ] **Étape 1 : écrire le module**

Créer `hosts/srv-1/services/odoo.nix` :

```nix
{ config, lib, pkgs, ... }:
{
  services.caddy.virtualHosts."odoo.srv-1.augendre.info".extraConfig = ''
    import common_headers
    import internal
    handle /websocket {
      reverse_proxy localhost:8072
    }
    handle {
      reverse_proxy localhost:8069
    }
  '';

  services.odoo = {
    enable = true;
    # Explicite : le défaut du module suit le stateVersion, et on ne veut pas qu'un
    # bump fasse changer Odoo de version majeure sans jouer les migrations.
    package = pkgs.odoo19;
    # domain reste null : Caddy fait le reverse proxy, on ne veut pas que le module
    # allume nginx à côté.
    settings.options = {
      db_host = "ag56382-001.eu.clouddb.ovh.net";
      db_port = 35458;
      db_name = "odoo";
      db_user = "odoo";
      db_sslmode = "require";
      # Pas de dbfilter : voir « Le piège du dbfilter »
      http_interface = "127.0.0.1"; # défaut 0.0.0.0 en 19.0 — sans ça, Odoo court-circuite Caddy
      unaccent = true; # extension activée à la main dans l'espace client OVH
      db_maxconn = 4; # 6 processus × 4 = 24 connexions au pire, cf. la spec
      workers = 3;
      limit_time_real = 120; # la base est distante, les requêtes traînent
      proxy_mode = true;
      # list_db = false est déjà le défaut du module.
      # db_password est volontairement absent : il arrive par PGPASSWORD, sans quoi
      # il finirait en clair dans le store, world-readable, dans un dépôt public.
    };
  };

  # Le module allume un PostgreSQL local en dur dont on n'a pas l'usage : la base est
  # chez OVH. Rien d'autre sur srv-1 ne veut de postgres local.
  services.postgresql.enable = lib.mkForce false;
  # Mais l'unité odoo met `config.services.postgresql.package` dans son PATH, pour le
  # pg_dump de la sauvegarde intégrée — et cette option n'a plus de valeur une fois le
  # service désactivé. On la pose sur la version qu'OVH fait tourner : pg_dump refuse de
  # sauvegarder un serveur plus récent que lui. Rien n'est installé pour autant.
  services.postgresql.package = pkgs.postgresql_17;

  # odoo19 tire python3.12-pypdf2-3.0.1 : six CVE, fork abandonné de pypdf, aucun
  # correctif amont possible. Exception assumée, cf. la spec. Épinglée à la version
  # exacte pour qu'elle échoue bruyamment le jour où elle n'est plus nécessaire.
  nixpkgs.config.permittedInsecurePackages = [ "python3.12-pypdf2-3.0.1" ];
  systemd.services.odoo = {
    requires = lib.mkForce [ ]; # pointait sur postgresql.target, qui n'existe plus
    after = lib.mkForce [ "network-online.target" ];
    wants = [ "network-online.target" ];
    serviceConfig.EnvironmentFile = config.age.secrets."odoo-env".path;
  };
}
```

Les deux routes sont dans des blocs `handle`, qui sont mutuellement exclusifs. Mélanger un `handle` et un `reverse_proxy` nu ferait dépendre le résultat de l'ordre des directives Caddy, qui n'est pas celui du fichier — et Discuss casserait silencieusement.

- [ ] **Étape 2 : importer le module**

Dans `hosts/srv-1/services/default.nix`, ajouter `./odoo.nix` à la liste `imports`, après `./esphome.nix`.

- [ ] **Étape 3 : évaluer — c'est ici que les `mkForce` se vérifient**

```bash
nix eval --raw .#nixosConfigurations.srv-1.config.services.odoo.package.name
nix eval .#nixosConfigurations.srv-1.config.services.postgresql.enable
nix eval .#nixosConfigurations.srv-1.config.systemd.services.odoo.requires
nix eval .#nixosConfigurations.srv-1.config.systemd.services.odoo.after
nix eval --raw .#nixosConfigurations.srv-1.config.services.postgresql.package.name
```

Attendu, dans l'ordre : `odoo-19.0.…`, `false`, `[ ]`, `[ "network-online.target" ]`, `postgresql-17.…`.

La dernière n'est pas décorative : sans `services.postgresql.package` posé explicitement, le `dry-build` échoue sur `The option 'services.postgresql.package' was accessed but has no value defined` — l'unité odoo la lit dans son `path` et l'option perd sa valeur quand le service est désactivé.

Si la première commande échoue sur `Refusing to evaluate package 'python3.12-pypdf2'`, c'est que le `permittedInsecurePackages` n'est pas dans la configuration, ou que la chaîne de version ne correspond plus. Dans le second cas, ne pas rafistoler la chaîne sans vérifier d'abord si `odoo19` tire encore pypdf2 : il se peut qu'il n'en ait plus besoin.

Si `services.postgresql.enable` vaut `true`, le `mkForce` n'a pas pris et le rebuild installerait un PostgreSQL inutile sur srv-1. Si `requires` contient encore `postgresql.target`, l'unité refusera de démarrer — la cible n'existe plus une fois postgres désactivé.

### Tâche 5 : déploiement et initialisation

**Fichiers :** aucun. Opérations sur srv-1.

**Interfaces :**
- Consomme : tout ce qui précède.
- Produit : un `odoo.service` démarré, et la réponse à la troisième inconnue de la spec (quel uid tourne réellement).

- [ ] **Étape 1 : déployer**

Depuis srv-1, dépôt à jour :

```bash
nh os switch .
```

- [ ] **Étape 2 : vérifier l'uid, et corriger le propriétaire du secret si besoin**

```bash
systemctl show odoo -p User -p DynamicUser
systemctl status odoo
```

Le module pose `DynamicUser = true` **et** déclare `users.users.odoo`. systemd n'alloue dynamiquement que si l'utilisateur n'existe pas, donc `User=odoo` statique est le résultat attendu, et le secret agenix par défaut est lisible.

Si le service échoue sur une erreur de permission en lisant l'`EnvironmentFile`, ajouter dans `hosts/srv-1/age/default.nix` ou dans `odoo.nix` :

```nix
age.secrets."odoo-env".owner = "odoo";
```

Si l'uid est réellement dynamique, le repli est `DynamicUser = lib.mkForce false;` **et** `services.odoo.settings.options.data_dir = "/var/lib/odoo/data";` **et** l'ajout de `/var/lib/odoo` aux `paths` de `hosts/srv-1/services/restic.nix` — sans quoi le filestore sort de la sauvegarde, `/var/lib/private` ne le couvrant plus.

- [ ] **Étape 3 : initialiser la base, si la tâche 2 ne l'a pas déjà fait**

Si l'étape 1 de la tâche 2 s'est terminée en code 0, la base est déjà initialisée : sauter cette étape.

Sinon, sur srv-1 :

```bash
systemctl stop odoo
cfg=$(systemctl show odoo -p Environment --value | tr ' ' '\n' | sed -n 's/^ODOO_RC=//p')
sudo -u odoo env ODOO_RC="$cfg" PGPASSWORD='<le mot de passe>' \
  odoo -d odoo -i base --without-demo --stop-after-init
systemctl start odoo
```

On n'utilise **pas** `services.odoo.autoInit` : il passe `--init=INIT --database=odoo --db_user=odoo` en dur, où `INIT` n'est pas un module Odoo existant. Le comportement ne tient qu'au fait qu'Odoo logue un module inconnu et continue — trop fragile pour une base de comptabilité.

Depuis une machine du tailnet :

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://odoo.srv-1.augendre.info/web/login
```

Attendu : `200`.

- [ ] **Étape 2 : l'accès public ne fonctionne pas**

C'est la vérification qui compte le plus : Odoo va contenir de la comptabilité.

```bash
curl -sS --max-time 10 -o /dev/null -w '%{http_code}\n' \
  --resolve odoo.srv-1.augendre.info:443:<IPv4 publique de srv-1> \
  https://odoo.srv-1.augendre.info/web/login
```

Attendu : un échec de connexion (timeout ou connexion refusée), **pas** un `403`. Le snippet `(internal)` fait `bind` sur l'IP Tailscale : Caddy n'écoute pas du tout sur l'IP publique pour ce vhost, donc rien ne doit répondre. Un `403` signifierait que le `bind` n'a pas pris et que seul le filtre `client_ip` protège — à corriger avant d'aller plus loin.

- [ ] **Étape 3 : vérifier qu'Odoo lui-même n'écoute que sur la boucle locale**

```bash
ssh srv-1
ss -lntp | grep -E ':(8069|8072)'
```

Attendu : `127.0.0.1:8069` et `127.0.0.1:8072`, jamais `0.0.0.0:*`. Le défaut d'Odoo 19 est `0.0.0.0` : si `http_interface` n'a pas pris, Odoo est joignable directement sur l'IP publique de srv-1 et tout le `bind` Tailscale de Caddy ne sert à rien.

- [ ] **Étape 4 : se connecter et installer une application**

Se connecter à `https://odoo.srv-1.augendre.info`, changer le mot de passe administrateur, puis installer une application depuis le menu Applications (Facturation ou Comptabilité selon l'usage visé).

- [ ] **Étape 5 : Discuss en temps réel — la preuve que la route `/websocket` marche**

Ouvrir Discuss dans deux navigateurs connectés à deux comptes différents, envoyer un message depuis l'un. Il doit apparaître dans l'autre **sans rechargement**.

Si le message n'arrive qu'au rechargement, la route `/websocket` ne tape pas sur le port 8072 : relire le vhost Caddy.

- [ ] **Étape 6 : mesurer la latence, c'est le vrai verdict**

Ouvrir une liste un peu lourde (liste des factures, ou Paramètres → Techniques → Modèles). Chronométrer.

C'est le risque principal de l'architecture : Odoo émet plusieurs centaines de requêtes par page et sa base est à l'autre bout du réseau. Si une page met plusieurs secondes de façon reproductible, c'est cette architecture qui est en cause, pas un réglage — et la conclusion est qu'il faut un PostgreSQL local sur srv-1.

Repère utile pour trancher :

```bash
ssh srv-1
env PGPASSWORD='<le mot de passe>' nix shell nixpkgs#postgresql -c psql \
  -h ag56382-001.eu.clouddb.ovh.net -p 35458 -U odoo -d odoo \
  -c '\timing' -c 'SELECT 1;' -c 'SELECT 1;' -c 'SELECT 1;'
```

Un aller-retour sous la milliseconde est confortable. Au-dessus de 5 ms, multiplier par 300 requêtes donne déjà 1,5 s de latence pure par page : c'est le moment de reconsidérer.

## Si Odoo passe de « testé » à « adopté »

Hors périmètre de ce plan, listé pour ne pas l'oublier — le détail est dans la section « Hors périmètre » de la spec :

- Un timer `pg_dump -Fc` vers `/var/lib/private/odoo/odoo.dump` à 01:30 plus `"odoo.service"` dans les `servicesToStop` de `restic.nix`, pour que base et filestore atterrissent dans le même instantané restic. Le filestore seul est **déjà** sauvegardé : `/var/lib/private` est dans les chemins.
- Un check healthchecks, sur le modèle des autres services de srv-1.
- Un nom d'hôte sans `srv-1`.
- Le retrait de l'exception `permittedInsecurePackages`. Elle saute d'elle-même le jour où nixpkgs construit `odoo19` avec python313 : le `requirements.txt` d'Odoo 19 bascule sur `pypdf` dès Python 3.13, et sa couche d'adaptation (`odoo/tools/pdf/`) le gère déjà. À surveiller à chaque bump de nixpkgs.
- Une stratégie de montée de version Odoo (le passage de `odoo19` à `odoo20` n'est pas un simple rebuild : il faut jouer les migrations).
